# 0029. Icons are one generated Carbon sprite, reached only through a macro

- Date: 2026-08-03
- Status: accepted
- Rule: `_icon_sprite.html` is generated. Edit the glyph list in the script, never the sprite. Reach glyphs only through `ico.icon` / `ico.toggle`.

## Context

The site had no glyph vocabulary at all: `·`, `×`, `←`, `→`, `-`, and nothing else.

Set chosen by eye against five others on the real theme. [docs/icon-set-choice.md](../icon-set-choice.md) has the measurements, the licenses, and what Carbon costs: no draw-on animation is ever possible, because filled compound paths have no stroke to dash, and Carbon's optical-size grids are irrelevant here since only `svg/32` carries our glyphs.

## Decision

`templates/_icon_sprite.html` is generated by `tools/build_icon_sprite.py`, which downloads the pinned `@carbon/icons` 11.85.0 tarball from npm at build time. Nothing is vendored but the sprite, so a clean checkout reproduces it byte for byte.

`ico.icon(name)` and `ico.toggle(name)` in `_icons.html` are the only way to reach it, registered as an environment global **before** `ui`, because `.module` snapshots the globals and a macro module can therefore only see globals registered earlier. `ui.status_badge` draws a glyph.

## Three things that are load-bearing and non-obvious

1. The sprite is included **outside `#main-content`**, because a boosted navigation swaps only that region and a sprite inside it would leave every `<use>` on the page resolving to nothing, silently, with no error.
2. It is hidden with `display: none`, because the `hidden` attribute does **not** hide an inline `<svg>`: it lays out at 300×150 and shoves the page down. Measured.
3. Carbon SVGs declare no `fill` or `stroke` at all, which is the SVG default of solid black. The generator imposes a `currentColor` contract on whatever package it is fed, reading stroked-versus-filled off the geometry rather than trusting the set.

`tests/test_icons.py` pins all three, plus "every name a template asks for exists".

## Motion, wanted and bounded

The user's position: reading "no dark patterns" as "no animation" is *"grossly overkill"*; confetti is the line.

Four CSS-only mechanisms, no JavaScript, all gated on `prefers-reduced-motion`: `.icon-press` (transform on `:active`), `.icon-swap` (outline to solid cross-fade on hover and `.is-active`), `.icon-spin` (running and loading only), and `.disclosure`.

Press is the one that matters on the feedback row, for a non-obvious reason: those controls **replace themselves over htmx**, so a transition on the result state would never play. The press animates the old element, before the swap, which is exactly when the reader is looking.

`.disclosure` animates the two `<details>` on the provenance page open and closed, and needs **both** of two primitives or it silently degrades to an instant toggle: `interpolate-size: allow-keywords`, without which `height: auto` has no number to interpolate towards and the transition is skipped, and `transition-behavior: allow-discrete` on `content-visibility`, without which the content stops being painted on the first frame of the close and an empty box collapses after it. `interpolate-size` is **inherited** and is deliberately not on `:root`, since that would make every `auto` on the site animatable. The caret is a sprite glyph rather than the native `::marker`, because a marker cannot be transformed; `list-style: none` removes the native one, so a `.disclosure` that forgot its caret would have no affordance at all, which a test pins. Under reduced motion the rotation stays, because it is a state indicator rather than motion, and nothing travels.

Live-verified 2026-08-03 against `/post/476/provenance`: 8 distinct intermediate heights opening (0 to 887px) and 8 closing, `content-visibility` still `visible` throughout the collapse, caret at `rotate(90deg)` open and none closed, and with reduced motion emulated the box read 0px 20ms after the click.

## Size is one knob

`--icon-scale`, 1.5. Icons inherit font-size from the control they sit in, so zoom and OS scaling carry them, but 1em reads *smaller* than the words beside it, because a glyph fills the whole em box while text only reaches cap height. The user runs 4K at 125% Windows and 150% Firefox.

## The admin rule is stricter, at the user's instruction

"Prioritise accuracy and clarity here." A **domain** action keeps its word and may only gain a glyph, since nothing is universally understood as "triage" or "propose vocabulary". Icon-only is allowed for genuinely universal actions (pin, edit, toggle, delete), each carrying `title` **and** `aria-label`, and never as the only place a **state** is readable, so the enabled chip and the "pinned" text stay. Status badges get a glyph beside the word, driven by the same tone mapping as the colour so the two cannot disagree. Both rules are regression-tested.

Every job control also gets a distinct glyph, distinct **within its group**, since that is the level a reader compares at; sharing across groups where the meaning matches is fine. The chain arrow is sized `calc(0.85rem * var(--icon-scale))` rather than a font size of its own, because it is doing an icon's job and should grow when the iconography does (13.6 to 20.4px measured).
